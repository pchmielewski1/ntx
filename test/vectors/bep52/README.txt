BEP52 (BitTorrent v2) test fixtures.

Everything here is generated by a script in test/scripts/ and is deterministic;
re-run the script to regenerate. The C tests read these files at run time and never
hard-code their values.

1. Torrent fixtures - test/scripts/bep52_gen.py

   single_16k/        pure v2, one file, 16 KiB pieces
   multi_v2/          pure v2, several files (root-level file and a subdirectory), 128 KiB pieces
   hybrid_ok/         hybrid (v1 and v2 in one info dict), one file, 16 KiB pieces
   hybrid_bad_order/  hybrid, several files, where the v1 file order differs from the v2
                      tree order (a client must reject it)

   Each directory holds:
     meta.torrent   the complete bencoded .torrent (announce, info, and "piece layers"
                    where the format has them)
     <file data>    the payload files, at their tree-relative paths
     manifest.txt   expected values, one "key: value" per line:

   fixture / kind / piece_len / np_total / addr_end / data_size
                  fixture name, kind, piece length in bytes, total number of pieces,
                  end of the per-file-aligned address space, total payload bytes
   ih_full        SHA-256 of the info dict (32 bytes, hex)
   ih_trunc       first 20 bytes of ih_full (hex); used on the wire by pure v2 torrents
   ih_sha1        SHA-1 of the info dict (20 bytes, hex); the v1 swarm of a hybrid torrent
   file: idx= fp= np= len= root= path=
                  one line per file, in tree order: index, first piece, piece count,
                  length, Merkle root (hex), path
   layer: idx= <hex>
                  piece layer of file idx (only for files longer than one piece)
   piece: idx= v2=<hex> [v1=<hex>]
                  expected hash of each global piece index
   magnet: <fixture> <btmh_only|dual>
                  names a magnet case; the following "magnet:?xt=..." line is its URI

   Used by: test/t_bep52_*.c, t_merkle.c, t_magnet.c, t_hash_exchange.c.

2. Hash-exchange messages - test/scripts/bep52_hash_msgs.py

   hash_request_leaf.bin, hash_request_piece_layer.bin, hash_reject.bin,
   hashes_omitted_proof_layers.bin, hash_request_illegal_length.bin,
   hash_request_illegal_index.bin

   Each is one complete framed peer-wire message (4-byte big-endian length, message id
   21 = hash request, 22 = hashes, 23 = hash reject). Each .bin has a .meta.json next
   to it describing the framing, the decoded fields, whether the message is legal, and
   how the contents were derived.

   Used by: test/t_hash_msg.c.
